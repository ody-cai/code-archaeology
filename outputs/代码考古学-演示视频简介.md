## 一、标准版（约 320 字 · 推荐用于作品提报表单）

我们不告诉你「为什么」，只告诉你「哪里已经没人能说清为什么」。

代码考古学做的是一台**信息丢失审计**仪表。每个仓库的地层下都埋着一段历史：谁加了什么、什么又被整体拆掉了、哪些文件一直在原地打转。这类信息只活在提交历史里，读代码本身永远看不到。这个工具先剥离 AI 大量生成造成的沉积物，再把人类决策的痕迹摊开，量化一个几乎没人量化过的指标——这个代码库的知识，还能不能被下一个人接过去。

本视频分为五个部分：项目概述与真实测试数据展示、网页版演示、Mac 版应用演示、Win 版应用演示、CLI 版演示。

全部结论都在**两个公开仓库的现场数据**上跑出来并留痕，没有一条合成数据：openclaw/openclaw（60 次提交，98% 为人类决策，风险分 0/100）与 ody-cai/topfo（7 处已核实的「被放弃的尝试」，9 个文件原地打转）。它的价值落在三个真实场景：投资并购前的技术尽调、新人接手前的交接清单、项目复盘。

9,395 行自研代码、零第三方依赖、181/181 单元测试通过、8 个 API 端点。同一套引擎有网页、命令行、HTTP API 三种形态，命令行支持 `--fail-on-risk` 风险阈值，可以直接接进 CI 当一道闸门。

## 三、详版（约 780 字 · 用于需要展开说明的场合）

### 一段话

「我们不告诉你『为什么』，只告诉你『哪里已经没人能说清为什么』。」

代码考古学（Code Archaeology）是一个面向 Git 提交历史的分析工具。代码走到今天，地层下层是各时期的真实改动，上层是 AI 大量生成带来的沉积物；工具先用一条流水线把沉积物剥掉，再把人类决策的痕迹挖出来摊平，输出一份可复核的结论：这个仓库的知识可继承性如何，风险集中在哪几个文件。

### 视频结构（五部分）

1. **项目概述与真实测试数据** —— 问题定义（读代码看不到的三类信息）、三段流水线（信噪分离 → 多模型分工 → 证据接地靠代码）、三种产品形态与已核实数据。
2. **网页版演示** —— 在线上入口现场提交仓库，查看风险因子拆解、提交演化时间轴、文件改动热度与「地层里的证据」逐条清单。
3. **Mac 版应用演示** —— 桌面客户端。
4. **Win 版应用演示** —— Windows 桌面客户端，现场分析 ody-cai/topfo。
5. **CLI 版演示** —— 一条命令跑完同一条流水线，输出可直接用于交接与评审。

### 实测数据（两个公开仓库，无一条合成数据）

- **openclaw/openclaw**：60 次提交压缩在 2 小时 15 分 47 秒内，约 26.5 次/小时；人类决策占比 98%，机器人提交仅 2%；8 位作者中一人占 80%（47 次提交、19,278 行改动、294 个文件）；风险分 0/100。
- **ody-cai/topfo**：7 处「被放弃的尝试」全部核实，拆除内容与当初新增内容重合 93%–100%，存活最短 1 小时 2 分、最长 2 小时 30 分；9 个文件原地打转（改动量大但净变化为零）。

### 工程实现

9,395 行自研代码、零第三方依赖、8 个 API 端点（其中 4 个可脱离前端单独复用）、181/181 单元测试通过。多模型分工：叙事者、假设者、审稿人由三家不同模型承担，产出的每条推断都必须引用真实提交 SHA，由程序统一校验——本轮实测 0 条编造引用、0 个无效提交号。命令行支持 `--fail-on-risk` 阈值，风险分超过阈值时以退出码 2 结束，可直接用于 CI 卡口。

### 已知边界（主动披露）

当前依赖 GitHub REST API，因此读不到私有仓库的完整历史，单次窗口上限 100 次提交；刻意不读 PR 与 Issue——保「不幻觉」优先于扩证据源。下一步改用本地 `git log`：零 API 成本、完整历史，且不接触对方仓库。
