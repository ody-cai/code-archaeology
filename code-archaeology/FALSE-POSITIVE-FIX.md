# 「被放弃的尝试」误报修复说明

> 2026-09-19 · 起因：对项目做可落地性复核时，逐条核对 GitHub 真实数据，发现核心指标存在假阳性。

## 问题

`src/miner.js` 的「被放弃的尝试」判定原为单一条件：某文件一次提交净增 ≥ 阈值，
随后 ≤ 45 天内又有一次净删 ≥ 阈值 60%。它只看**行数**，不看**内容**。

实测发现这个判据会把「实现被重写」误判为「方案被放弃」。

## 证据

用 GitHub API 逐条核对四次配对的真实 diff，计算「拆除侧删掉的行中有多少曾在新增侧出现」：

| 仓库 | 配对 | 重合率 | 真相 |
|---|---|---|---|
| chalk/chalk `source/index.js` | `4c304dd`(+19) → `5729845`(−35) | **14%** | 假阳性 |
| chalk/chalk `test/chalk.js` | `ff549c5`(+20) → `8a94e0e`(−36) | **31%** | 假阳性 |
| oa-system `AGENTS.md` | `d8ca09f`(+43) → `109fd2c`(−119) | **28%** | 假阳性 |
| oa-system `src/app/api/email/send/route.ts` | `b86cce0`(+58) → `7c78ec0`(−58) | **100%** | 真阳性 |

三条假阳性的具体情形：

1. **`5729845` 是 `4c304dd` 的直接子提交**，间隔 1 小时 20 分，提交信息为
   `Improve performance`。它重写了 `index.js` 的实现。核对当前 main 分支：
   `source/index.js:115` 有 `['underline' + capitalizedModel, 'underlineColor']`，
   `index.d.ts` 有 `underlineRgb` / `underlineHex` / `underlineAnsi256` / `underlineCurly`
   —— **「下划线样式」功能完整存在，且是当前核心特性**。功能没被放弃，是实现了被优化。
2. `8a94e0e` 是「Require Node.js 22」时对测试文件的整文件重写，原有断言被保留。
3. `109fd2c` 的提交信息是 `Restored to 'acd42d064...'`，一次**整仓回滚**。
   AGENTS.md 的 119 行是被这次全局操作连带清理的，不是有人决定放弃这个方案。

真阳性与假阳性之间隔着约 50 个百分点，两簇不重叠。

## 修复

新增 `src/core/overlap.js`（纯函数、无网络、无模型依赖），把判定从「按行数猜」
升级为「按内容判」：

- **内容核实**：拆除侧删除的行中，出现在新增侧的比例 ≥ 50% 才算放弃；
  低于阈值判为「实现被重写」，计入 `abandonedRejected` 并**照常输出**。
- **排除整仓回滚**：提交信息匹配 `^restored?\s+to\s+'?[0-9a-f]{7,40}` 的提交，
  其连带删除计入 `globalReverts`，不归因为文件级放弃。
- **容错**：GitHub 对超大 diff 不返回 patch。拿不到 patch 时不下判断，
  保留为待核实线索 —— 不可核实 ≠ 假阳性，宁可保留可疑条目也不丢掉真阳性。

阈值 50% 取自上述实测分布，不是估计值。

同时修正展示层：

- 「存活 0 天」被删除。`0 天` 是 round 到整数天的产物，语义上自相矛盾 ——
  0 天意味着它从未活到能被放弃。改用真实时间戳算到分钟（`52 分钟` / `8 小时` / `3 天`），
  出现在 `bin/ca.mjs` 与 `public/render.js`。
- 页面新增「复核未通过」说明块，把**否定的判定**一并亮出。
  只展示「发现了什么」、不展示「否定了什么」的报告无法被复核。

## 结果

| 仓库 | 修复前 | 修复后 |
|---|---|---|
| chalk/chalk | 2 处「被放弃」（均为假阳性） | 0 处已核实，2 处已否定 |
| oa-system | 17 处「被放弃」（含 3 处假阳性、含整仓回滚连带） | 4 处已核实，3 处已否定，10 处整仓回滚单列 |

chalk 风险分由 63（高）降至 55（中）—— 降幅全部来自假阳性被剔除。
oa-system 的 Resend 邮件案例（真实放弃、间隔 52 分钟）保持通过。

## 顺带修掉的一个测试缺陷

`scripts/smoke-render.mjs` 原先用 `report.abandoned.length` 决定是否构造完整的合成分析层。
后果：仓库没有「被放弃的尝试」时（如 axios），叙事/假设/裁决/接地四个区块全部走降级路径，
被误报为「空输出」；而仓库恰好有假阳性条目时，夹具反而通过 ——
**假阳性掩盖了夹具自身的缺陷**，判定修准之后它才暴露。

已改为无条件构造完整结构，并补上降级路径的独立断言
（`renderAppraisal` 降级时应返回空，避免与叙事层的降级提示重复）。

## 验证

- 单元测试 **165 / 165 通过**（新增 8 项，含四个真实案例的固化回归）
- 冒烟测试两阶段全绿：`axios/axios`（无放弃条目）、`ody-cai/oa-system`（4 条放弃条目）
- 完整多模型流水线仍正常：假设层 4 条、证据接地 0 编造、审稿人照常质疑
- 阶段二新增契约断言：`abandonedRejected` / `globalReverts` 必须为数组，
  每条 `abandoned` 必须带 `verified` 布尔标志

## 已知限制（未修复，需在路演中如实说明）

内容核实证明的是「删除的确实是先前新增的那些行」，**不证明「这是一个被放弃的方案」**。

例：oa-system `src/app/login/page.tsx` 的 `5456fc1`(+41) → `8813f17`(−36) 通过了内容核实，
但 `8813f17` 是「实现站内即时通讯系统」的一次大重构 —— 它重写登录页是重构的一部分，
并非有人决定放弃登录页的那个改动。内容对得上，语义上不是「放弃」。

缓解手段是系统的分层设计：假设层对这类案例标注**置信度「低」**，
并强制写明「提交信息未说明原因，以下为基于改动范围的推断」，
把判断权交回给人。这一层不做断言，只提供带证据的候选线索。
